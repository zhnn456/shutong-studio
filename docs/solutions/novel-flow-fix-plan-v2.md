## 1. 一句话结论

**六个真问题里，有四个是「能力已存在但没长在默认路径上」，改的是编排与可见性，不需要新模型能力；另两个是工程债（授权已闭环、合并已工程化一半）。**

所以本计划的重点不是"造功能"，而是：**把已有的 commit / 回写 / 流水线技能 / 变更对话，变成用户不用记指令就会发生的默认行为。**

## 4. 修复计划

排序原则：**用户体感 × 复用已有底座 × 是否被上游改动干扰**。上游 0.10.0 已按批次合并进 `unstable`（`656af92` 等），本轮不再安排合并，只保留"合并工程化收尾"。

### 阶段 0 · 立刻（合计 3–4 天，全部是"改默认路径"）

#### P0-1 额度与入口（A1–A6 一揽子）

**目标**：新用户第一次点"开始"必须能建出一本书，且任何时候都知道自己还能建几本。

| 改动 | 落点 | 说明 |
|---|---|---|
| 首启种子不计入免费额度 | `app_initialization.dart:74,79-81` + `novel_quota_gate.dart` | 示例作品标记为 `demo` 来源并从额度统计剔除；或免费版首启不种小说、只种剧本 |
| 草稿不计额度 | `novel_quota_gate.dart:43-45` | 统计加 `where((n) => !n.draft)`；草稿单独计数并给"清理草稿"出口 |
| 额度常驻可见 | 首页顶栏 / 新建对话框 | 「本月可创建 1/1（免费版）」+ 满额时按钮态变化 |
| 失败三出口 | `home.dart:381-405` | 弹窗改为**可关闭但保留输入**：`升级完整版` / `改用剧本` / `清理草稿后重试`；想法文本回填输入框 |
| 托盘同文案 | `system_tray_service.dart:259` | 先 `on NovelFreeLimitException` → `settingsLicenseFreeLimitReached`；其余走 `libraryCreateNovelFailed`，全部 i18n |
| 演示作品移出主流程 | 首页按钮区 | 收进设置-调试分区（演示页 M5 的诉求） |

**验收（可测）**：
1. 全新安装、未授权 → 点"从想法开始"→ 建书成功，书架出现 1 本，额度条显示 `1/1`。
2. 再点一次 → 输入框内容仍在，三个出口可点，`novels` 行数不变。
3. 点"清理草稿"后同一条想法可成功建书。
4. 托盘路径在满额时给出额度文案，不是"创建小说失败"。

#### P0-2 开书向导封顶 3 轮（B1/B2）

**目标**：向导最多 3 轮提问，第 4 轮必须产出"最小可写集合"（书名 + 主角一句话 + 一句钩子），然后进编辑器。

| 改动 | 落点 |
|---|---|
| 新增 `setup_round` 计数（会话级状态） | `lib/shared/services/novel_actions.dart:203` 一带的 `novel_onboarding` 状态；读取侧 `chat_turn_runner.dart:1553-1561` |
| 闸门改造：从"会话数≤3"改为"轮次≤3 且未完成" | `setup_phase_gate.dart` |
| 第 3 轮后强制收敛：注入"停止提问、输出开书摘要"系统指令 | `setup/SKILL.md` 增补硬规则（不改 6 步结构，只加封顶与收尾） |
| 取消卡片 = 结束向导 | `ask_user_card.dart:398,413`：`onCancel` 回调置 `novel_onboarding.completed=true` 并跳过 setup 段 |

**验收**：连续答"不知道"到底 → 第 3 轮后再无提问，直接给开书摘要；中途取消卡片 → 本轮之后不再注入 setup 段（看 prompt 日志）。

#### P0-3 上下文预算 12k（C1–C3）

**目标**：写章请求 `input_tokens ≤ 12,000`，且只装四块：近 2–3 章摘要 / 出场角色当前状态 / 未回收伏笔 Top3 / 本章大纲目标。

| 改动 | 落点 |
|---|---|
| 新增 `context_budget.dart`：任务级预算 + 四块装配 + 按最后出场章降权 | 新文件，`lib/shared/services/ai/context_budget.dart` |
| `excludeFromAi` 字段（实体/文档可被排除） | 内容库表加列 + 实体编辑页勾选框 |
| 常驻注入白名单 | 组装器读取白名单集合，始终注入 |
| 下调压缩线 | `agent_context_manager.dart:26` 的系数从 `0.8` 改为按模型窗口 40–50%；`agent_config.dart:46` 预算单发上限同步 |

**验收**：同一本书第 3 章请求 `input_tokens ≤ 12,000`；被排除实体零出现；简报四块齐全且不含 5 章前未活跃角色；`cache_read` 下降。

#### P0-4 写后回执条（D1）

**目标**：写完一章不发任何指令，编辑器顶部自动出现「本章新增伏笔 2 / 角色状态 1・查看差异」。

| 改动 | 落点 |
|---|---|
| 复用 `PendingChangesDetailDialog` | `novel_editor.dart:1169-1188` 已有 `showPendingChangesDialog` |
| 触发点：本轮 commit 落库后 | `working_overlay.dart:739`（`autoSaveCommit` 写入点）之后发一个会话级事件 |
| UI：常驻条 + 点开即 dialog + 「忽略」 | `novel_editor.dart` 顶部区 |

**验收**：`change_commits` +1 后回执条出现；点开可逐条确认；拒绝的条目不落库。

**风险**：P0-3 与 P0-4 都动上下文与 overlay，**必须串行做**，不要并行改同一文件。

#### P0-5 「写本章」按钮 + 前置阻断（E1）

**目标**：一个按钮跑完 简报 → 确认 → 起草 → 审查 → 回填，缺章纲/缺设定时**禁止进起草**。

| 改动 | 落点 |
|---|---|
| 按钮 + 步骤机（每步可停可退） | 编辑器工具栏 + 新控制器（复用 `chapter-write-pipeline/SKILL.md` 四步） |
| 前置校验 | 无章纲 → 按钮置灰 + 「去补章纲」；无主角设定 → 「先定主角」 |
| 每步产物落盘可查 | 简报落 `Documents`，审查结果落聊天气泡 |

**验收**：一键走完四步且中途可停；缺章纲时按钮不可用并给出跳转；每步产物可在历史里查到。

#### P0-6 概览「下一步建议」卡片（E2，便宜且立刻见效）

按完成度动态给一个跳转按钮：无设定→"先写题材定位"；有设定无大纲→"搭全书大纲"；有卷纲无细纲→"写前 3 章细纲"；有细纲无正文→"写第 1 章"；有正文→"写下一章 / 去 AI 味 / 审查"。
落点：`workspace/hero.dart` + `novel_overview.dart:1227`（已有顺序引导，改为可点击）。

4. **AGPL-3.0**：上游 `looplj/reveric` 为 AGPL；我们作为网络/桌面分发方，改动需保留源码可得性。P3-1 的品牌脚本**不得移除上游版权头与 LICENSE**。
5. **版本号文案**：对用户只讲"更快、更省、更顺"，不提授权与防破解细节。
6. **不做清单**（防止功能堆砌）：不自研模型；不做社交/拼字/稿酬；不把向量 RAG 当主线（先做 P0-3 结构化装配，P2-5 再补检索）；不新增设定页类型；不追"一键整本生成"。

### P0-0-A 取消向导 = 设定不落盘（且不告知）

**实测**：取消第 2、3 轮问卷后写完两章，库中 `agent_rules=0 / documents=0 / character_profiles=0 / foreshadowings=0`，主角名从「周砚」漂成 AI 临起的「陈默」。

**根因（三层，缺一层都会复发）**：

1. **写入时机**：`assets/bundled_skills/setup/SKILL.md:88,105,112` 全部写的是"用户确认后分别写入"。第 1 轮已答的根决策本可以落盘，但"整轮问卷被取消"被模型读成"整批未确认"，于是前面答过的也一起不写。
2. **取消语义**：`ask_user_card.dart:398,413` → `PendingAskUser.complete(cancelled:true)`（`pending_ask_user.dart:82-90`），只是把这张卡结束掉，**没有"先把已确认项落盘"的收尾动作**，向导也没被标记结束（所以取消第 2 轮还会出第 3 轮）。
3. **无完成度状态**：`setup_phase_gate.dart` 只按 `maxNovelChatSessions=3` 判会话数，没有"已确认 N 项 / 还缺 M 项"的持久化字段，所以既无法"先落盘已答"，也无法事后补。

**修法（按序，前三步必须一起上，否则只是换个地方丢）**：

| 步 | 改动 | 文件 |
|---|---|---|
| 1 | SKILL.md 加硬规则：**每轮答完即增量落盘该轮能确定的项**（根决策→元数据→规则），不等全部问完；"取消"= 已答项照写 + 停止追问，不是"整批作废" | `setup/SKILL.md`（改第 88/105/112 行附近措辞 + 新增"取消语义"小节） |
| 2 | 取消回调改为：`persistConfirmedSoFar()` → 写 `novel_onboarding.completed=true` → 才结束卡片；卡片上明写"跳过只会保留已确认的 N 项，其余留空" | `ask_user_card.dart:398,413`、`setup_phase_gate.dart` |
| 3 | 增加向导完成度字段（已确认项清单 + 缺口），供收尾"补设定"入口读取 | `novel_onboarding` 状态（`novel_actions.dart:203` 一带） |
| 4 | 编辑器给"补设定"入口：检测到 `characters=0` 且有正文时，概览出现"补主角/补伏笔"按钮 | `novel_overview.dart:1227`、`workspace/hero.dart` |

**验收**（照复验步骤重跑即可）：第 1 轮答完即取消 → 第 3 轮不再出现 → 库中至少有 `profile.title/tags/description` + 1 条根决策规则 → 第 1 章写完全库仍保留这些 → 主角名固定为问卷里的名字，不再由 AI 临起。

**风险**：增量落盘可能写出半成品（如"分类待定"）。约束：只写用户已明确回答的字段，未回答的一律留空并记入缺口清单，不猜、不填默认值。

### P0-0-B 「待发送」消息卡死（其实是互锁，不是慢）

**实测**：AI 执行中发消息 → 灰卡"待发送"停 3 分钟无提示；中途有挂起问卷卡时更久。

**根因（精确到机制）**：

- 消息不是丢，是进了 `queuedMessages` 队列并 `sendOnNextTurn=true`（`panel.dart:370-380`、`chat_session_controller.dart:1694-1697`）。
- 队列**只在当前 turn 结束后**由 `_flushQueuedMessageAfterRequest` 消费（`chat_session_controller.dart:1715-1728`）。
- 而挂起问卷卡会把当前 turn **一直 hold 住**，超时上限 **30 分钟**（`pending_ask_user.dart:24`）。
- 于是：**问卷卡等用户点；用户消息等 turn 结束 → 互等**。写章时 turn 本身也要几分钟，叠加起来就是实测的 3 分钟乃至更久。
- 界面侧只有 `aiQueuedMessage*` 三个短文案（`composer.dart:699-752`），没有"AI 正在处理，完成后自动发送"的状态说明，也没有可见倒计时，所以作者以为已发出。

**修法**：

| 步 | 改动 | 文件 |
|---|---|---|
| 1 | 队列卡文案升级为状态条：「AI 正在写作（已 2 分 10 秒）· 这条消息将在本轮结束后自动发送」+「立即发送」+「撤回」(现有 `onSendQueuedMessageNow/onClearQueuedMessage` 已有入口，仅需把文案与状态做实) | `composer.dart:682-760` |
| 2 | **打破互锁**：`sendQueuedNow` 与"新消息到达"两条路径都先检查 `pendingAskUserRequests`，存在则先 `complete(cancelled)` 结束挂起卡，再发消息 | `chat_session_controller.dart:1715` 附近 + `ai_providers.dart:726-767` |
| 3 | 缩短问卷超时：30 分钟 → 3 分钟无人应答即自动"跳过本题"并继续（提示已记录超时），超时不再是静默黑洞 | `pending_ask_user.dart:23-24` |
| 4 | 写章这类长任务补步骤级进度（"读取第 1 章 → 组装简报 → 起草 → 审查"），让"在处理"和"卡死"可区分 | `working_overlay.dart` / 新步骤控制器（与 P0-5 共用） |

**验收**：问卷卡挂起时发消息 → 3 秒内该卡自动结束且消息开始执行；无问卷时发消息 → 状态条出现秒级计时，本轮结束后自动发出；「立即发送」可打断当前轮；连续两次复验不再出现"干等 3 分钟"。

**风险**：自动结束挂起卡会让 AI 在缺答案时继续写。约束：取消结果里带上"用户已发新消息，按新消息执行，缺口沿用已有设定"，并让 AI 在回复首句声明哪些设定缺失——即"降级但要显式"。
